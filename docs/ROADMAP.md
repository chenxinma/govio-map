# Govio Map 技术路线图

> 版本 v1.0 · 2026-09 · 状态：提案
> 适用范围：面向**企业内数据分析用户**（企业内部的分析师 / 数据开发 / 业务分析岗）的演进规划。

---

## 1. 一个核心判断

Govio Map 今天已经能"跑通"：自然语言 → SQL → DataFrame → 图表/报告的画布闭环是完整的。
企业分析师不采用一个工具，从来不是因为功能不够多，而是因为三个问题的答案是否定的：

| 分析师的真实疑问 | 现状 |
|---|---|
| **"AI 给我的这个数，我敢直接交给领导吗？"** | 不敢。SQL 由 LLM 生成，无法一键复跑验证，结果与口径没有留痕 |
| **"它算的'活跃用户'和公司定义的'活跃用户'是一回事吗？"** | 不确定。知识图谱里有指标定义和数据标准，但只是"可查询"，不约束 AI 的取数口径 |
| **"我做的这张分析画布，同事明天能接手吗？"** | 不能。画布和会话锁在个人本机，没有共享与交接机制 |

**因此本路线图的主线只有一条：把 Govio Map 从"个人 AI 取数工具"进化为"结果可信、口径统一、成果可交接的团队分析工作台"。**
三个阶段分别回答上面三个问题，每个阶段只有一个北极星指标，做完一个再启动下一个。

---

## 2. 演进原则（反堆砌约束）

1. **一个阶段只解决一个信任问题**。任何不服务于当前阶段北极星指标的需求，无论多"顺手"，一律进 Backlog 不进排期。
2. **优先复用已有资产**：画布节点模型（`src/types/index.ts`）、govio-cli ObserveStore、知识图谱（govio-meta / govio-query）、会话持久化（`.govio/sessions/*.jsonl` + canvas sidecar）。新功能优先表现为"已有节点的属性增强"而非"新节点类型"。
3. **能力下沉**：凡是 govio-cli 能做的（SQL 执行、比对、探查），前端不重复实现；凡是知识图谱已有的（指标、标准、血缘），AI 不重新发明。
4. **每阶段交付必须包含退出判据**（北极星指标达标线），未达标不进下一阶段。

---

## 3. 阶段路线

### Phase 1 —— 可信分析："这个数敢不敢交"

**目标用户场景**：分析师用自然语言完成一次月度经营取数，需要向业务方交付，且交付物要经得起质询（"这个数怎么算的？"）。

**北极星指标**：**可复现率** —— 交付的分析画布中，任意 DataFrame 节点可一键复跑且结果一致的比例 ≥ 95%。

| 关键结果 | 说明 | 主要落点 |
|---|---|---|
| KR1 分析留痕（Analysis Manifest） | 每个 DataFrame/Report 节点固化：SQL 全文、数据源版本、执行时间、行数校验和、模型与提示摘要。写入 canvas sidecar，随会话持久化 | `server/session-history.ts`、`govio-canvas.ts` 节点事件、`src/store/canvas-store.ts` |
| KR2 一键复跑与漂移提示 | DataFrame 节点支持"复跑"：重执行固化 SQL，对比行数/校验和，不一致时在节点上标记漂移警告而非静默覆盖 | govio-cli `observe load` 复用、节点 UI（`DataFrameNode.tsx`） |
| KR3 取数确认门 | 高风险动作（写文件 `-o`、跨库查询、全表扫描）沿用并强化 permission-manager 确认流，确认记录进 Manifest | `server/permission-manager.ts`（安全分支已扩展危险命令闸门） |
| KR4 交付导出 | 画布一键导出为自包含 HTML/PDF 报告（节点+血缘+Manifest 附录），离线可看 | 新导出模块，仅消费已有节点数据 |

**明确不做**：不做定时调度、不做告警、不做数据质量规则引擎——那是治理平台的事，不是分析工作台的事。

---

### Phase 2 —— 语义层集成："口径是不是公司口径"

**目标用户场景**：不同部门分析师问"上季度华东区活跃客户数"，得到的 SQL 口径一致，且能追溯到数据标准与指标定义。

**北极星指标**：**口径命中率** —— 涉及已入库指标/标准的取数请求中，AI 生成 SQL 自动引用图谱定义（而非自造口径）的比例 ≥ 90%。

| 关键结果 | 说明 | 主要落点 |
|---|---|---|
| KR1 图谱作为 Prompt 约束而非查询目标 | 会话启动时按引用表/问题实体自动注入相关指标定义、字段标准、枚举码值（现在需用户显式让 AI 去查图谱） | `server/ws-handler.ts` 上下文注入、govio-query skill |
| KR2 口径溯源节点属性 | SQL 节点记录"本次口径引用了哪些图谱实体"（指标 ID / 标准 ID），画布上血缘边可区分"数据血缘"与"语义血缘" | 节点数据模型扩展，`src/types/index.ts` |
| KR3 口径冲突检测 | AI 生成的 SQL 与图谱指标定义不一致时（如"活跃"过滤条件不同），在 SQL 节点上给出黄色警示与差异说明，用户可选择采纳图谱口径 | 比对逻辑下沉 govio-cli，前端只展示 |
| KR4 元数据导入常态化 | govio-meta 导入流程支持增量更新与校验报告，保证图谱新鲜度（口径命中率的供给侧） | `skills/govio-meta`、CLI 侧 |

**明确不做**：不自建指标平台/语义层存储——图谱（Ladybug/FalkorDB）就是语义层，只做"注入与校验"，不做第二套定义入口。

---

### Phase 3 —— 成果可交接："同事能不能接手"

**目标用户场景**：分析师 A 离职/转岗，其画布上的专项分析（数百节点、多轮会话）由分析师 B 无损接手并继续演进。

**北极星指标**：**画布复用率** —— 每周被第二人打开并产生新节点的共享画布占比 ≥ 30%（团队试点内）。

| 关键结果 | 说明 | 主要落点 |
|---|---|---|
| KR1 画布脱离本机 | 会话 + canvas sidecar + Manifest 从 `.govio/sessions/` 本地文件升级为团队存储（先做文件服务器/对象存储同步，不急于上数据库） | `server/session-history.ts` 存储抽象层 |
| KR2 只读分享 → 可续写分享 | 第一步只读链接（含复跑能力，依赖 Phase 1 Manifest）；第二步 fork 续写，血缘上保留"派生自"关系 | WS 协议扩展、前端会话列表 |
| KR3 多用户与权限 | 后端从单会话单用户模型升级为按用户隔离会话；接入企业 SSO（OIDC），数据源权限跟随用户身份 | `server/agent.ts` 会话管理重构（最大工程量，放最后） |
| KR4 服务化部署形态 | 在 Electron 单机版之外提供 Docker 部署的 Web 版（前端已是纯 Web 架构，主要是后端多租户化与安全边界，安全基线见 `security/hardening` 分支） | 部署与运维文档 |

**明确不做**：不做实时多人协同编辑（Google Docs 式光标同步）——分析工作的交接是"异步接手"，不是"同时编辑"，协同编辑成本极高且不符合场景。

---

## 4. 非目标清单（Anti-Roadmap）

以下方向**永久不做**，出现即拒绝，防止产品漂移为四不像：

- ❌ 通用 BI 仪表盘（拖拽报表、定时大屏）——与 FineBI/Superset 等竞争无胜算，且偏离"分析过程工作台"定位
- ❌ ETL 编排调度（Airflow/DolphinScheduler 的能力）
- ❌ 通用 Notebook / 代码 IDE——画布 + 对话是本产品形态，不退回 Jupyter
- ❌ 自研大模型 / 模型托管——只做模型接入与路由
- ❌ 移动端 App
- ❌ 面向 C 端 / 公网多租户 SaaS——定位是企业内部署

---

## 5. 横切工程项（伴随各阶段，不单独立项）

| 项目 | 动机 | 时机 |
|---|---|---|
| 安全基线落地 | CSWSH/路径穿越/API key 泄露等修复（`security/hardening` 分支）合入 main，作为 Phase 3 多用户的前置 | 立即 |
| WS 协议契约化 | `docs/specs/07-websocket-protocol.md` 升级为版本化 schema + 双端类型生成，防止多用户改造时协议腐化 | Phase 2 起 |
| 前端 bundle 拆分 | 当前单 chunk 6MB（plotly 全量），按节点类型懒加载 | Phase 1 KR4 前 |
| 测试基建 | 核心链路（节点事件流、Manifest 序列化、图谱注入）建立集成测试；当前仅有 session-history 自检 | 每阶段交付的一部分 |
| 安装包签名与自动更新 | Electron 企业分发的基本要求 | Phase 3 |

## 6. 里程碑与退出判据

```
Phase 1 (可信分析)      Phase 2 (语义层)        Phase 3 (可交接)
─────────────────────  ─────────────────────  ─────────────────────
Manifest + 复跑         图谱注入 Prompt         画布团队存储
交付导出                口径溯源与冲突检测       只读分享 → fork
退出: 复现率 ≥95%       退出: 口径命中 ≥90%     退出: 复用率 ≥30%
   (试点团队 4-6 周验证)    (依赖图谱数据质量)       (依赖 SSO 与部署形态)
```

**依赖与风险**
1. Phase 2 强依赖客户侧图谱数据质量（指标/标准入库率）——若供给侧不足，先做 Phase 1 + Phase 3 KR1/KR2（只读分享不需要语义层）。
2. Phase 3 的多用户改造是架构级变更（单例 session → 会话池），必须在 WS 协议契约化之后启动，否则协议债务会放大。
3. LLM 生成 SQL 的正确率是所有指标的天花板：Phase 1 的复跑/校验和与 Phase 2 的口径约束，本质上都是在工程上对冲模型不可靠性，而非假设模型可靠。

---

## 7. 一句话版本

> **先让结果可复现（Phase 1），再让口径可信赖（Phase 2），最后让成果可交接（Phase 3）——其余一切需求都是噪音。**
